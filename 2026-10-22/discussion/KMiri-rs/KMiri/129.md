# KMiri: 修复 #102；双周会

* 修复星绽堆 borrow tag 失效问题：Rust 的 Box 会产生 unique bortag，因此在 heap slot 中，通过 box 指针衍生的指针访问 box 之外、slot 之内的部分，不具有 box 衍生的 unique bortags。上游 Rust 希望 Box 不再那么特殊产生 unique tag。但当下修复的方式是抹除 unique tag，通过 `ptr as usize as *mut u8` 暴露出处、创建 `&mut slot_slice`、写入 0 清除 slot 数据等方式重新产生 bortag。
  * https://github.com/KMiri-rs/asterinas/pull/25
* Mir 调试器：在 GC 中保留 bortag spans（否则会出现 bortag 存在，但看不到对应的源码）
  * https://github.com/KMiri-rs/miri/pull/36
* 通过调用 yield_now 修复主线程早于子任务退出问题
  * https://github.com/KMiri-rs/KMiri/pull/123

# KMiri：调研 TockOS 和 vivo-BlueOS

* TockOS：
  * 下周重点查看对这个系统的支持，因为它相对容易适配，比如
    * 工具链版本号与星绽一致，都是 `2026-07-21`
    * 单地址空间：基于 MPU 而不是 MMU，无虚拟地址。难点在于内存布局与星绽完全不同，但相对直接，没有那么多内存阶段（甚至没有采用 Rust 的 liballoc 库进行灵活的动态内存分配）
  * 分析记录（AI  生成）
    * [TockOS 的整体架构](https://github.com/KMiri-rs/KMiri/discussions/128)
    * [TockOS 内存分配策略](https://github.com/KMiri-rs/KMiri/discussions/126)
    * [TockOS 的异步模型](https://github.com/KMiri-rs/KMiri/discussions/127)
    * [TockOS 编译记录](https://github.com/KMiri-rs/KMiri/discussions/125)
* vivo BlueOS：
  * 这个系统比较难支持，因为
    * rustc 很旧，版本号为 `nightly-2024-11-22`，并且维护了自己的 [rustc](https://github.com/vivoblueos/rust) 仓库，添加 `thumbv7m-vivo-blueos-newlibeabi`、`riscv64-vivo-blueos` 之类专属于 blueos 的 targets，甚至（貌似）基于此重用了 Rust 的标准库
    * 采用非 cargo 方式编译：基于 repo、ninja、gn 这类 andriod 构建工具编译内核，需手动调用 rustc
  * 分析记录：[编译 vivo-blueos](https://github.com/KMiri-rs/KMiri/discussions/124)

结论：相比于 BlueOS，优先支持 TockOS
