## Body

> 什么时候 CTFE 的 CompileTimeMachine 会介入？它和 MiriMachine 同时存在吗？这两个 Machine 分别用在什么场景

两个 Machine **同时编译进同一个二进制,但不同时求值**。它们的存在形态、触发条件、职责区分如下。

## 本质区别:一条指针语义的分界线

这是整个问题的根。两种机器只在 `Provenance` 类型上不同,而 `Provenance` 直接决定 `OFFSET_IS_ADDR`:

|                   | `CompileTimeMachine`                      | `MiriMachine`                                   |
| ----------------- | ----------------------------------------- | ----------------------------------------------- |
| Provenance        | `CtfeProvenance`(一个 `AllocId` + 位标记) | KMiri 的 `Provenance`(`AllocId`/`Wildcard`/...) |
| `OFFSET_IS_ADDR`  | **`false`**                               | **`true`**                                      |
| 指针 offset 含义  | 相对分配器内部的偏移                      | 就是绝对物理地址                                |
| int2ptr cast 结果 | `Pointer::without_provenance(addr)`       | `Some(Provenance::Wildcard)`                    |
| `WILDCARD`        | 无                                        | `Some(Wildcard)`                                |

我刚确认了 rustc 源码(`pointer.rs:166`):`CtfeProvenance` 的 `OFFSET_IS_ADDR = false`,注释写得很直白——

> With the `CtfeProvenance` as provenance, the `offset` is interpreted *relative to the allocation*, so ptr-to-int casts are not possible (since we do not know the global physical offset).

这就是**为什么 const 里的 `0x10000000` 必须被剥掉出处**:CTFE 的指针是相对分配器的,它根本不知道全局物理地址,所以 int2ptr 只能"transmute"成一个无出处的值。

## 分别用在什么场景

**`CompileTimeMachine` — 编译期求值(const 求值)**
- 求值顶层 `const`(你的 `UART0_BASE`)、`static` 初值、常量折叠、`const fn` 调用、`#[rustc_promotable]` 的常量提升、泛型参数求值等。
- 由 rustc 的 **global const eval query** 驱动(`eval_to_...` 查询),在 rustc 内部完成。Miri 启动前,**大多数 const 早已被它求值并 `intern` 进元数据**。
- 它不跑用户程序的语句、不发运行时 UB;只在"求这个常量"这个封闭任务里工作,结果被冻结成 `ConstAllocation`(一个 `Allocation`)。

**`MiriMachine` — 解释执行待测程序**
- 从入口函数(`kmiri` 的 `entry_fn`,即 Tock 内核)开始,一条条解释 MIR,检查 UB、管理内存、模拟外设(你的 `alloc_addresses`/`mirch` 都属于它)。
- Miri 通过 `eval_entry` 创建 `InterpCx` 时实例化的是 `MiriMachine`,而不是 `CompileTimeMachine`。

## 它们同时存在吗?

**同时存在于同一个可执行文件 / 同一进程里,但不在同一时刻求值。**

关键点:KMiri 进程里,rustc 的所有 const-eval 查询(query)都用 `CompileTimeMachine`;Miri 自己的解释循环用 `MiriMachine`。两者的 `InterpCx` 是**独立创建的**,各自的"全局内存"互不相通——CTFE 求出的常量以只读 `ConstAllocation` 的形式传给 Miri,Miri **读取的是冻结后的整数,不重新走 CTFE 的 cast 逻辑**。所以:

- 程序运行期间,`MiriMachine` 正常解释。
- 当 Miri 遇到某个"还没有被求值过的 const/泛型常量"(比如运行中触发的泛型实例化、关联常量),它会**内部再调一次 rustc 的 const-eval query**,这次照样用 `CompileTimeMachine` 去求值,拿到冻结值后再塞回自己的内存里。这就是"共存但分工"的实际形态。

## 为什么会把 `UART0_BASE` 交给 CTFE 而不是 MiriMachine

因为 `UART0_BASE` 在 `uart.rs:13`,**顶层 `pub const`**,没有任何运行时参数(不是泛型、不依赖运行时值),所以它**在编译期就被 CTFE 求值完毕并 intern 进元数据**。KMiri 运行时读这条常量,直接拿的是 `Scalar::Int(0x1000_0000)` —— 出处已经丢在 CTFE 阶段了。**KMiri 的 `ptr_from_addr_cast`(`MiriMachine` 的)根本没机会参与**,这就是上一轮定位的结论。

## 一句话总结

`CompileTimeMachine` 负责"这个常量是什么"(编译期、相对分配器、无 wildcard、int2ptr 剥出处),`MiriMachine` 负责"这段程序怎么跑"(运行期、绝对地址、有 wildcard、int2ptr 给 Wildcard)。`UART0_BASE` 属于前者处理,所以它到 Miri 手里已经是无出处的整数。

如果你想验证"到底是 CTFE 还是 Miri 在求值这条 const",可以在 KMiri 的 `ptr_from_addr_cast`(`alloc_addresses/mod.rs:644`)打个 log —— 如果这条诊断期间它**没打印** `0x10000000`,就证明是 CTFE 在做,而不是 MiriMachine。你之前加的 log 没看到地址,恰好证实了这一点。
