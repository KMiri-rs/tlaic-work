# TockOS 大量 `&'static` 和 `&'static mut` 像是过度设计

## Body

> 你给的构造方式确实有用，并且合理。但这里大量采用 static_init! 暴露 &'static mut 引用，而且 QemuRv64VirtClint 之类的结构带 &'static 引用，这貌似违反了 Rust 的语义： &'static
mut T 和  &'static T 意味着永久借用，那么根据借用规则，它可以派生自一个独占的永久借用，并在一些阶段 reborrow 成共享的永久借用（这被 Rust 允许吗？？？是 Rust
明确定义的吗？），但实际上这些永久引用非常危险：mmio 映射到地址属于外部无出处的，并且可以被硬件直接修改，这打破了 &'static mut
的独占性（因为持有它的期间实际被别的东西写），也打破了 &'static 的共享性（因为它假设永久不可变，但实际可能被修改）。当然这些引用内部是可变的（使用了
UnsafeCell，从而等价于裸指针，但大量结构和接口采用 'static，有点没必要，甚至滥用，直接用裸指针更容易理解，也更符合 Rust 习惯）

这是个很好的设计批判，让我把几个问题分别讲清楚。

## 1. `&'static mut T` reborrow 为 `&'static T` 是否 Rust 明确定义的？

是，这是 Rust 定义的合法操作。reborrow 规则是：持有 `&'a mut T` 时可以派生出 `&'b T`，条件是 `'b ≤ 'a`。`'static` 是最长的 lifetime，所以可以：

```rust
let r: &'static mut T = ...;
let s: &'static T = &*r;   // 合法：reborrow
```

但代价是——由于派生出的 `&'static T` 永远存活，`r` 这个 `&mut` 从此被 freeze，借用检查器保证你永远不能再用 `r` 做任何可变操作。对于 `'static` 而言，"reborrow 到 `'static T`" 在语义上等价于"永久放弃了 mutable 访问"。所以这不是"在某些阶段 reborrow"，而是"一次性不可逆地转换"。

## 2. 但 MMIO 下这整套实际是谎言

你指出的核心矛盾是真实的。Rust 引用的语义承诺：

| 引用类型 | 承诺                                                     |
| -------- | -------------------------------------------------------- |
| `&T`     | 共享不可变；编译器可假设数据不变（alias analysis、优化） |
| `&mut T` | 独占可变；编译器可假设无其他访问者                       |

MMIO 两条都违反——硬件随时在读写寄存器，既不"独占"也不"不可变"。

Tock 的做法之所以"能跑"，是因为 `register_structs!` 生成的寄存器类型（`ReadWrite<u32>` 等）内部包了 `Cell<u32>`，也就是 `UnsafeCell`。**`UnsafeCell` 是 Rust 中退出 `&T` = 不可变 这个承诺的唯一合法方式。** 一旦内部有 `UnsafeCell`，编译器不再对 `&T` 背后的数据做"不变"假设，volatile 读写才能正确工作，硬件修改才不会被优化掉。

所以实际的语义图是：

```
&'static StaticRef<ClintRegisters>
         │
         └── ptr: NonNull<ClintRegisters>
                          │
                          └── 内部全是 Cell<u32> (UnsafeCell)
                                          │
                                          └── 等价于裸指针 + volatile rw
```

`'static` 在这里实际只是在说"这个指针在程序的整个生命周期内有效"，而不是在表达任何所有权或可变性的语义保证。这个信息量用 `'static` 来携带确实是借用了 Rust 的 lifetime 语法但并不真正符合其语义。

## 3. 为什么 Tock 要用 `'static` 而不是裸指针？

你说直接用裸指针更诚实，从语义角度完全正确。Tock 的选择有其历史和工程考量：

**用 `'static` 的好处：**
- 结构体里带 `'a` 字段时，编译器能帮你检查"这个 driver 不能活得比它引用的外设更长"——这在非 MMIO 场景（比如 callback 引用）下是真实有效的保证
- `static_init!` 给的 `&'static mut T` 保证"只有一份"——这在 no-std、no-alloc 的环境里替代了 `Box<T>` 的作用，而且零运行时开销
- 接口类型（`hil::time::Alarm<'a>` 等）可以用 lifetime 参数在类型层面约束 callback 的生命周期

**裸指针的代价：**
- 结构体定义和 API 签名里到处是 `*const T` / `*mut T`，使用点必须手写 `unsafe`
- 跨模块传递时失去了任何 lint 和 lifetime 错误提示

**但你说的"滥用"批评也成立：**  
对于 MMIO 寄存器基址这个具体场景——`StaticRef<ClintRegisters>` 内部是 `UnsafeCell`，`'static` 实际表达不了任何有意义的 Rust 保证，此时 `'static` 确实是在"借用"一个语法形式而语义已经掏空了。这是 Tock 设计上的一个取舍：用 `'static` 统一了"外设指针"和"真实 Rust 对象引用"两种东西，换来了 API 的统一性，但代价是让读者要花力气区分哪些 `'static` 是"真正的借用检查语义"，哪些是"永久有效的裸指针的别名"。

## 结论

- reborrow：Rust 明确定义，合法，但对 `'static` 而言是不可逆操作
- MMIO + `&'static`/`&'static mut`：靠 `UnsafeCell` 维持实际正确性，`'static` 本身的 Rust 语义承诺在此被刻意放弃
- 裸指针更诚实：对 MMIO 基址这一点你完全正确；Tock 的选择是工程上的统一性换取了语义诚实性
