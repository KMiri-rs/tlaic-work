## Body

本文档梳理 kmiri 在解释执行过程中对任务（线程）调度的整体逻辑，涵盖调度主循环、线程状态机、CPU 绑定与切换、kmiri 自定义的线程/CPU 调度 shim，以及 GenMC 模式下的调度委托。

## 一、总体架构

```
eval.rs 入口
   └─ ecx.run_threads()          # 解释执行主循环（scheduler.rs）
        └─ ecx.schedule()        # 每轮循环决定"下一步做什么 / 跑哪个线程"
             ├─ GenMC 模式 → genmc_ctx.schedule_thread() 委托给 GenMC
             └─ 普通模式 → 调度策略（线程轮转 + kmiri CPU 切换）
        └─ SchedulingAction::ExecuteStep
             └─ ecx.step_current_thread()   # 单线程执行一步
```

关键数据结构均位于 `ThreadManager`（[`src/concurrency/thread.rs`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs)）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `active_thread` | `ThreadId` | 当前活动线程 |
| `active_cpu` | `usize` | 当前活动 CPU 编号（kmiri 扩展） |
| `next_cpu` | `Option<usize>` | 下一轮要切换到的 CPU（kmiri 扩展） |
| `cpu_to_threads` | `[Option<ThreadId>; CPU_NUM]` | CPU → 线程映射（kmiri 扩展） |
| `cpu_local_base` | `[usize; CPU_NUM]` | 每 CPU 的局部变量基地址（kmiri 扩展） |
| `next_thread` | `[Option<ThreadId>; CPU_NUM]` | 每 CPU 的下一个待执行线程（kmiri 扩展） |
| `yield_active_thread` | `bool` | 主动让出标记 |
| `fixed_scheduling` | `bool` | 是否使用固定（轮转）调度而非随机调度 |
| `threads` | `IndexVec<ThreadId, Thread>` | 所有线程（含已终止的） |
| `stack_pool` | `StackPool` | 可复用栈内存池（Best-Fit 策略） |

其中 `CPU_NUM` 定义在 [`src/machine.rs:494`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/machine.rs#L494)，当前为 `2`。

## 二、解释执行主循环：`run_threads`

**位置**：[`src/concurrency/scheduler.rs:199`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/scheduler.rs#L199)

```rust
fn run_threads(&mut self) -> InterpResult<'tcx, !> {
    loop {
        // 1. 处理 Ctrl+C 中断
        if CTRL_C_RECEIVED.load(Ordering::Relaxed) {
            this.machine.handle_abnormal_termination();
            throw_machine_stop!(TerminationInfo::Interrupted);
        }
        // 2. 调度：决定下一步动作与线程
        match this.schedule()? {
            SchedulingAction::ExecuteStep => {
                // 2a. kmiri：页表类型页被写入后的占位检查（pt_checker，当前为 todo）
                if let Some(paddr) = this.machine.pt_checker { ... }
                // 2b. 单线程执行一步
                this.step_current_thread()?;
                // 2c. 调试器交互
                if let Some(handle) = &this.machine.debugger { ... }
            }
            SchedulingAction::SleepAndWaitForIo(duration) => {
                // 3. 所有线程都阻塞：等待 I/O / 睡眠
                if this.machine.communicate() {
                    this.poll_and_unblock(duration)?;
                } else {
                    this.machine.monotonic_clock.sleep(duration.expect(...));
                }
            }
        }
    }
}
```

循环每轮只执行**一步**（`step_current_thread`），然后回到 `schedule()` 重新调度。这一步可能推进 MIR 语句、执行终结器（terminator）或调用 foreign function shim。

### 2.1 单步执行：`step_current_thread`

**位置**：[`src/concurrency/scheduler.rs:181`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/scheduler.rs#L181)

```rust
fn step_current_thread(&mut self) -> InterpResult<'tcx> {
    let this = self.eval_context_mut();
    if !this.step()? {
        // 当前线程无法继续执行（栈为空），运行 on_stack_empty 回调
        match this.run_on_stack_empty()? {
            Poll::Pending => {} // 继续运行
            Poll::Ready(()) => {
                this.terminate_active_thread(TlsAllocAction::Deallocate)?;
            }
        }
    }
    interp_ok(())
}
```

- `step()` 是 rustc 解释器核心的 MIR 单步执行；若返回 `false` 表示该线程当前无可执行内容（例如线程函数返回、栈耗尽）。
- `run_on_stack_empty` 调用线程的 `on_stack_empty` 回调（如主线程的 `MainThreadState`、普通线程的 TLS 析构回调）。回调返回 `Poll::Ready` 时调用 `terminate_active_thread` 结束该线程。

### 2.2 线程终止：`terminate_active_thread`

**位置**：[`src/concurrency/thread.rs:999`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L999)

终止流程：

1. 断言栈为空，将线程状态置为 `Terminated`，并记录 `stack_bottom` 用于栈回收。
2. 释放该线程的 TLS 分配（`Deallocate` 或 `Leak`）。
3. 通知数据竞争检测器（Vclocks 或 GenMC）。
4. 唤醒所有 `BlockReason::Join(thread_id)` 阻塞在该线程上的线程（`unblock_thread`）。
5. **kmiri 栈回收**：在 `stack_pool` 中找到 `base_vaddr == stack_bottom` 的 `StackState`，标记 `using = false`，使该栈区域可被后续线程复用（Best-Fit）。

## 三、调度器：`schedule`

**位置**：[`src/concurrency/scheduler.rs:53`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/scheduler.rs#L53)

`schedule()` 返回 `SchedulingAction`（`ExecuteStep` 或 `SleepAndWaitForIo`）。逻辑分三大部分。

### 3.1 GenMC 模式：完全委托

若 `data_race.as_genmc_ref().is_some()`，调度权交给 GenMC（详见第七节），此处不赘述。

### 3.2 kmiri 扩展：线程 + CPU 切换（最高优先级）

```rust
// kmiri: thread and cpu switch
if let Some(res) = thread_manager.schedule_switch_thread_and_cpu() {
    return res;
}
```

**位置**：[`src/concurrency/thread.rs:799`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L799)

该函数在普通调度策略**之前**执行，专门处理 kmiri 的显式/延时切换请求：

```rust
pub fn schedule_switch_thread_and_cpu(&mut self) -> Option<InterpResult<'tcx, SchedulingAction>> {
    // (a) 当前活动线程已终止：强制切回主线程
    if let ThreadState::Terminated = self.threads[self.active_thread].state {
        self.active_thread = ThreadId::MAIN_THREAD;
        return Some(interp_ok(SchedulingAction::ExecuteStep));
    }
    // (b) 当前 CPU 有待执行的 next_thread（由 miri_switch_to 设置）
    if let Some(id) = self.next_thread[self.active_cpu] {
        assert_ne!(self.active_thread, id);
        let old_id = self.active_thread;
        self.active_thread = id;
        self.cpu_to_threads[self.active_cpu] = Some(id);
        self.next_thread[self.active_cpu] = None;
        if self.threads[self.active_thread].state.is_enabled() {
            // 若同时有待切换的 CPU，一并处理
            if let Some(next_cpu) = self.next_cpu {
                self.active_cpu = next_cpu;
                self.active_thread = self.cpu_to_threads[next_cpu].unwrap();
                self.next_cpu = None;
            }
            return Some(interp_ok(SchedulingAction::ExecuteStep));
        } else {
            // 目标线程不可执行 → 全局死锁
            return Some(Err(MachineStop(GlobalDeadlock)).into());
        }
    }
    // (c) 仅 CPU 切换请求（由 maybe_switch_cpu 随机触发）
    if let Some(next_cpu) = self.next_cpu {
        self.active_cpu = next_cpu;
        self.active_thread = self.cpu_to_threads[next_cpu].unwrap();
        self.next_cpu = None;
        return Some(interp_ok(SchedulingAction::ExecuteStep));
    }
    None // 无切换请求，交给普通调度策略
}
```

要点：

- `miri_switch_to(task)` 通过 `thread_map`（task 结构地址 → `ThreadId`）找到目标线程，调用 `ThreadManager::switch_to(thread_id)` 把该线程 ID 写入 `next_thread[active_cpu]`；到下一次 `schedule()` 时由本函数真正切换。
- `cpu_to_threads[cpu]` 记录了每个 CPU 上"当前运行的线程"；`kern_miri_init_ap` 创建 AP 线程时通过 `set_ap_init_thread` 写入该映射。
- 若被切换到的线程已经阻塞/终止，kmiri 直接报 `GlobalDeadlock`（不会去尝试别的线程）。
- 当前活动线程终止时无条件回主线程。

### 3.3 普通调度策略（Loom 风格）

1. **继续当前线程**：若当前线程 `is_enabled()` 且未请求让出（`!yield_active_thread`），直接返回 `ExecuteStep`，不切换线程。
2. **处理延迟就绪更新**：`DelayedReadinessUpdates::process(this)?`。
3. **I/O 事件轮询**：`communicate()` 开启时 `poll_and_unblock(Duration::ZERO)` 处理 host I/O 事件。
4. **过期 deadline**：`unblock_expired_deadlines()?` 唤醒超时线程，返回距下一个 deadline 的时间。
5. **选择下一个线程**：

```rust
let mut threads_iter = thread_manager
    .all_threads()
    .skip(thread_manager.active_thread().index() + 1)
    .chain(thread_manager.all_threads().take(thread_manager.active_thread().index() + 1))
    .filter(|(_id, thread)| thread.is_enabled());
// 从当前线程之后开始轮转（rotate_left），保证公平
let new_thread = if thread_manager.fixed_scheduling() {
    threads_iter.next()      // 固定调度：取第一个
} else {
    threads_iter.choose(rng) // 随机调度：均匀随机选
};
if let Some((id, _)) = new_thread {
    if thread_manager.active_thread() != id {
        thread_manager.set_active_thread(id);
    }
}
thread_manager.yield_active_thread = false; // 完成本次 yield
```

6. **无可用线程**：全部终止则 `unreachable!()`；有超时回调则 `SleepAndWaitForIo(Some(sleep_time))`；有 host I/O 阻塞线程则 `SleepAndWaitForIo(None)`；否则 `throw_machine_stop!(GlobalDeadlock)`。

## 四、线程状态机

**位置**：[`src/concurrency/thread.rs:117`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L117)

```
        create_thread / start_regular_thread
                     │
                     ▼
                 ┌─────────┐   block_thread（Join/Sleep/Mutex/Condvar/RwLock/
    enable_thread │  Enabled │◄──────────── Futex/InitOnce/Readiness/Eventfd/IO/Genmc）
                 └─────────┘
                     │        ▲
              step 结束 │        │ unblock_thread（如 join 完成、mutex 解锁、超时等）
                     ▼        │
                 ┌─────────┐
                 │ Blocked │
                 └─────────┘
                     │（stack 为空 + on_stack_empty 返回 Ready）
                     ▼
               ┌───────────┐
               │ Terminated │──► 回收 TLS、唤醒 join 线程、栈回收(stack_pool)
               └───────────┘
```

`ThreadState` 三态：

- `Enabled`：可被调度执行。
- `Blocked { reason: BlockReason, deadline: Option<Deadline>, callback }`：阻塞在某个同步原语上，附带解阻塞回调。
- `Terminated`：执行结束（保留在 `threads` 中，供 join 查询）。

`BlockReason` 枚举定义了阻塞原因（Join/Sleep/Mutex/Condvar/RwLock/Futex/InitOnce/Readiness/Eventfd/VirtualSocket/IO/Genmc），`unblock_thread` 会断言唤醒原因与阻塞原因一致。

### 让出与抢占

- **主动让出**：`yield_active_thread()`（[`thread.rs:1354`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L1354)）只置 `yield_active_thread = true`，不立即切换——真正的切换发生在下一个基本块的 `schedule()` 中，避免在 MIR 语句执行中途换栈。`miri_spin_loop`、主线程关闭时的 `Yield` 状态等都会触发。
- **随机抢占**：`maybe_preempt_active_thread()`（[`thread.rs:1362`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L1362)）在每个基本块结束（[`machine.rs:2045`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/machine.rs#L2045)）被调用：非固定调度且 `random_bool(preemption_rate)` 为真时让出当前线程。kmiri 默认 `preemption_rate = 0.0`（关闭随机抢占，见 [`eval.rs:209`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/eval.rs#L209)）。

## 五、kmiri 的 CPU 调度扩展

kmiri 在经典 Miri 单"CPU"线程轮转之上引入了**多 CPU（`CPU_NUM = 2`）与 CPU 局部存储**的模拟。相关机制：

### 5.1 CPU 随机切换：`maybe_switch_cpu`

**位置**：[`src/concurrency/thread.rs:1371`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L1371)

```rust
fn maybe_switch_cpu(&mut self) {
    let this = self.eval_context_mut();
    if this.machine.rng.get_mut().random_bool(0.02) {   // 2% 概率
        let next_cpu = (this.machine.threads.active_cpu + 1) % CPU_NUM;
        if this.machine.threads.cpu_to_threads[next_cpu].is_some() {
            this.machine.threads.next_cpu = Some(next_cpu);
        }
    }
}
```

在每个基本块结束时（`machine.rs:2047`）调用。命中后设置 `next_cpu`，在下次 `schedule()` 的 `schedule_switch_thread_and_cpu` 分支 (c) 中执行切换——活动 CPU 变为下一个 CPU，活动线程变为 `cpu_to_threads[next_cpu]` 上的线程。

### 5.2 CPU 局部存储（CPU-local）

- 每 CPU 有一段物理内存区域（`cpu_local_segment_size`），起始地址 `cpu_local_start_addr()`（内核静态区之后，见 [`mirch/config.rs`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/mirch/config.rs#L212)）。
- `ThreadManager` 初始化时把所有 CPU 的 `cpu_local_base` 都指向 `kernel_code_paddr_to_vaddr(cpu_local_start_addr())`（[`thread.rs:576`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L576)）。
- shim 接口：
  - `kern_miri_get_cpu_local_base`（[`foreign_items.rs:834`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/shims/foreign_items.rs#L834)）：返回当前活动 CPU 的 `cpu_local_base[active_cpu]`。
  - `kern_miri_set_cpu_local_base`（[`foreign_items.rs:844`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/shims/foreign_items.rs#L844)）：设置当前 CPU 的 `cpu_local_base`。

### 5.3 任务创建与切换 shim

这些 shim 是 kmiri 内核侧（如 asterinas）通过 `extern "Rust"` 调用的接口：

| Shim | 作用 | 实现位置 |
|------|------|----------|
| `kern_miri_init_ap(cpu_id, func, args, task, stack_end, stack_size)` | 为指定 CPU 创建 AP（应用处理器）线程，绑定 CPU，记录 `thread_map[task] = id` | [`foreign_items.rs:851`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/shims/foreign_items.rs#L851) |
| `miri_create_new_thread(func, args, task, stack_end, stack_size)` | 创建普通新线程并记录 `thread_map` | [`foreign_items.rs:874`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/shims/foreign_items.rs#L874) |
| `miri_switch_to(task)` | 显式切换到指定任务对应的线程（记录到 `next_thread[active_cpu]`） | [`foreign_items.rs:895`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/shims/foreign_items.rs#L895) |

**切换时序示例**（内核代码调用 `miri_switch_to(task_b)`）：

```
基本块 N：miri_switch_to(task_b)
   └─ thread_map 查得 thread_id_b → ThreadManager::switch_to(thread_id_b)
        └─ next_thread[active_cpu] = Some(thread_id_b)   // 延迟，不立即切
基本块 N 结束：maybe_preempt_active_thread / maybe_switch_cpu
下一次 schedule()：
   └─ schedule_switch_thread_and_cpu 分支 (b)
        └─ active_thread = thread_id_b；cpu_to_threads[cpu] = thread_id_b
        └─ 返回 ExecuteStep → 执行线程 B
```

注意 `miri_switch_to` 目标线程**必须**存在且处于 Enabled，否则报 `GlobalDeadlock`。这是 kmiri 依赖内核自身协作式调度（`miri_switch_to`）的主要体现。

### 5.4 线程的 CPU 亲和性继承

创建子线程时（[`thread.rs:965`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L965)），若 `thread_cpu_affinity` 已初始化，子线程继承父线程的 `CpuAffinityMask`（`sched_setaffinity`/`sched_getaffinity` 实现，见 [`shims/unix/foreign_items.rs`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/shims/unix/foreign_items.rs)）。

## 六、非主线程的栈分配与复用

**位置**：[`src/concurrency/thread.rs:516`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L516)

kmiri 为非主线程维护一个 `StackPool`（栈内存池），采用 **Best-Fit** 策略：

```rust
fn get_stack_range(&mut self, stack_mem_size: u64) -> Range<u64> {
    // 1. 从池中找最小的、未使用且 size >= 所需大小的栈
    let best_fit = self.stack_pool().iter().enumerate().rev()
        .filter(|(_, s)| !s.using && s.size >= stack_mem_size)
        .min_by_key(|(_, s)| s.size);
    if let Some((idx, _)) = best_fit {
        let stack = &mut self.stack_pool()[idx];
        stack.mark_using();
        return stack.range();
    }
    // 2. 池中没有合适的 → 在 kernel stack 区分配新栈
    let id = self.stack_pool.next_stack_id;
    self.stack_pool.next_stack_id += 1;
    let step = stack_mem_size as usize;
    let base = kernel_stack_end_addr();
    let start = base + id * step;
    let end = base + (id + 1) * step;
    // ... paddr → vaddr 转换后入池并标记 using
    range
}
```

- 栈区物理范围：`kernel_stack_start_addr()..kernel_stack_end_addr()`（即内核代码段的末尾区域）。
- 默认栈大小：`config_stack_mem_size() = 0x4000`（16 KB），可用 `kmiri.toml` 的 `stack_mem_size` 覆盖（[`mirch/config_toml.rs:14`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/mirch/config_toml.rs#L14)）。
- 线程终止时（`terminate_active_thread`）按 `stack_bottom` 找到对应 `StackState` 并 `clear_using()`，栈区域回到池中供后续线程复用。
- 主线程栈固定为 `kernel_code_paddr_to_vaddr(kernel_stack_start_addr())..(kernel_stack_end_addr())`（[`thread.rs:571`](https://github.com/KMiri-rs/miri/tree/f3577b25f4c542ce6790896e815a95150ff5b11c/src/concurrency/thread.rs#L571)），不参与复用。

## 七、GenMC 模式下的调度委托

当启用 GenMC 模式（`data_race.as_genmc_ref().is_some()`）时，`schedule()` 完全交由 GenMC：

```rust
loop {
```
