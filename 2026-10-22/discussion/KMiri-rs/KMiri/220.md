# BlueOS 的内核测试框架 `test_harness`

## Body

**`test_harness`（crate 名 `blueos_test_macro`）是 BlueKernel 的自定义测试框架**——它是一套建立在 Rust 标准「custom test frameworks」特性之上的 proc-macro，专门用于在 `no_std`、多核、无操作系统的环境下运行单元测试。

## 它的组成（两层）

**1. Rust 原生层：custom test framework**
`kernel/src/lib.rs` 里有三段配置（`kernel/src/lib.rs:39-42`）：

```rust
#![cfg_attr(test, no_main)]
#![cfg_attr(test, feature(custom_test_frameworks))]
#![cfg_attr(test, test_runner(tests::kernel_unittest_runner))]
#![cfg_attr(test, reexport_test_harness_main = "run_kernel_unittests")]
```

- 用 `feature(custom_test_frameworks)` 替换掉 Rust 自带的 libtest（自带的那套需要 `std`，这里用不了）。
- `test_runner` 指向 `kernel/src/lib.rs:770` 的 `kernel_unittest_runner`：它遍历 `tests: &[&dyn Fn()]` 依次调用，打印前后堆内存状态（`allocator::memory_info()`）、SP、线程信息，结束后 `write_coverage_data()` 并 `EXIT_SUCCESS` 退出——**在真实内核上下文（线程栈、内核堆上）跑测试**。

**2. 自定义宏层：`blueos_test_macro`**
`test_harness/src/lib.rs` 是 proc-macro crate，导出 4 个属性宏（`test_harness/src/lib.rs:28-67`）：
- `#[test]` —— 核心属性宏，生成测试体
- `#[only_test]` —— 只保留**第一个** `only_test`，其余删空（配合 `test_only!()` 用于单测调试）
- `#[test_only]` —— 函数式宏，调用后让所有 `#[test]` 变为空（构建非测试镜像时删掉全部测试）
- `#[ignore]` —— 直接展开为空，实现忽略

## 它如何"测试"

`#[test]` 宏把用户函数改造成（`test_harness/src/lib.rs:229-243`）：
1. 转包一层 `#[test_case]`，加上打印输出选择（`semihosting::println` 或 `defmt::println`，配合 QEMU 运行）；
2. 支持 **三个参数控制测例行为**（`test_harness/src/lib.rs:251-320`）：
   - `#[test(repeat = N)]` — 循环跑 N 次；
   - `#[test(thread = M)]` — 用内核自带的 `blueos::thread::spawn` 创建 M 个线程，用 `ConstBarrier` 同时起跑、`wait_until` 等全部完成（`test_harness/src/lib.rs:152-187`），并带一个 `Drop` guard 统计完成数。**这是它能在真实内核多线程上下文验证并发原语的关键**；
   - `thread=1, repeat=1` 则只是普通串行打印 `[ RUN ] / [ OK ]`。

## 调用链与构建

- 通过 `kernel/BUILD.gn:99` 和 `:132` 以 `proc_macro_deps` 挂进 `kernel_unittest` 二进制目标，rustflags 带 `--test`（`kernel/BUILD.gn:110-111`）；
- 实际调用点是 `kernel/src/lib.rs:124`：`use blueos_test_macro::{only_test, test};`，然后所有 `#[test]` 直接用这个宏。我之前统计的 kernel 268 个 `#[test]` 就是这些宏展开出来的；
- 它还在 `loader/tests/integration_test/` 里复用于**集成测试**（加载器在真机上跑 ELF）。

## 关键点：这个框架比标准 `#[test]` 多了什么

|          | 标准 libtest        | blueos_test_macro               |
| -------- | ------------------- | ------------------------------- |
| 运行环境 | 需要 `std`/操作系统 | `no_std`，跑在内核态            |
| 多线程   | 用 OS 线程          | 用内核 `blueos::thread::spawn`  |
| 输出     | stdout              | semihosting / defmt (QEMU 串口) |
| 测试编排 | `cargo test`        | 自定义 runner，检查堆/线程泄漏  |

所以它的本质是：**把标准测试框架的宏层换成自己写的 proc-macro，把 runner 换成在内核上下文里执行的 `kernel_unittest_runner`，从而让单元测试直接跑在真实的内核调度器、线程和内存分配器之上**。这解释了为什么 infra（纯数据结构，可在 miri 上测）与 kernel（依赖内核运行时）的测试分层如此清晰。
