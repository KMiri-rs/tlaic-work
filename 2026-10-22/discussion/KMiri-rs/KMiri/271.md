# Rust for Linux: Arc 和 ListArc

## Body

> 貌似这些 Arc 指针通常并不是 Rust 管理和创建的，而是从内核 C 代码创建，Rust 只是通过绑定进行了类型包装
好的，把上一个回答重新生成，文件位置统一换成基于该 commit 的永久链接。

对，你的直觉说对了一半，但**精确的边界要分两层**。我把 `Arc`/`ListArc` 从"谁创建/谁管理"这条线拆开看，结论是：

## 1. 引用计数本体确实是 C 的

`Refcount` 是 `bindings::refcount_t` 的透明包装（[`refcount.rs:22`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/rust/kernel/sync/refcount.rs#L22)）：

```rust
#[repr(transparent)]
pub struct Refcount(Opaque<bindings::refcount_t>);
```

inc/dec 全部走 C 绑定（[`refcount.rs:72`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/rust/kernel/sync/refcount.rs#L72)、[`:84`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/rust/kernel/sync/refcount.rs#L84)、[`:108`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/rust/kernel/sync/refcount.rs#L108)）：`bindings::refcount_inc` / `refcount_dec` / `refcount_dec_and_test`。这里确实借用了 C 的 `refcount.h` 的饱和计数语义（负数当"已损坏"处理），而不是 Rust 自己的 `AtomicI32`。

## 2. 但 Arc 的**分配**是 Rust 做的，不是 C

关键在 `Arc::new`（[`arc.rs:222`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/rust/kernel/sync/arc.rs#L222)）：

```rust
let value = ArcInner { refcount: Refcount::new(1), data: contents };
let inner = KBox::new(value, flags)?;   // Rust 内核分配器分配
let inner = KBox::leak(inner).into();
```

`ArcInner<T>` 是 Rust 定义的 `#[repr(C)]` 结构，把 refcount 和 data 放**同一次分配**里（[`arc.rs:146`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/rust/kernel/sync/arc.rs#L146)）。也就是说：**refcount 字段用的是 C 的语义，但它和对象本体一起是 Rust 用 `KBox` 分配的**——不是"C 代码创建了对象、Rust 只是包了一层"。

## 3. 真正的 C↔Rust 交接点是 `ForeignOwnable`

`Arc<T>` 实现了 `ForeignOwnable`（[`arc.rs:366`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/rust/kernel/sync/arc.rs#L366)）：

- `into_foreign()` → 把 Arc 变成 `*mut c_void` 交给 C 存着
- `borrow()` / `from_foreign()` → C 把裸指针还回来时，Rust 恢复出 `ArcBorrow`

所以是 **Rust 创建并拥有 Arc → 把裸指针递给 C → C 只拿裸指针在它自己的结构里转手 → 需要时再还给 Rust 重建所有权**。C 从不"创建"这个 Arc，它只持有 Rust 给它的指针。

## 4. 你印象里"C 管理的链表"其实是另一套 API

内核树里有两套链表，别混了：

|            | `rust/kernel/list.rs`（ListArc 那套） | `rust/kernel/interop/list.rs`（CList 那套） |
| ---------- | ------------------------------------- | ------------------------------------------- |
| 链表节点   | Rust 定义 `ListLinksFields`           | C 的 `struct list_head`                     |
| 谁创建     | Rust（`ListArc::pin_init`）           | **C 代码**，Rust 只是迭代                   |
| 你直觉对应 | ❌                                    | ✅                                          |

`interop/list.rs` 的 doc 里写得明明白白：`struct SampleItemC { int value; struct list_head link; }` 是 C 定义的，Rust 用 `#[repr(transparent)] struct Item(Opaque<SampleItemC>)` 去包装，靠 `bindings::INIT_LIST_HEAD`/`list_add_tail` 操作（[`interop/list.rs:44-65`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/rust/kernel/interop/list.rs#L44-L65)）。**这条链路才完全符合你说的"C 创建、Rust 包装"**。

同理 `rbtree.rs` 里 `Node<K,V>` 嵌了 `links: bindings::rb_node`（[`rbtree.rs:1430`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/rust/kernel/rbtree.rs#L1430)），C 的 rbtree 用 `container_of!` 反推回 Rust 的 `Node`——但即便如此，`Node` 本身（内含 `Arc<K,V>`）仍是 Rust 分配的，C 只碰内嵌的 `rb_node` 指针。

## 5. binder 是纯 Rust 结构

Rust 版 binder 的 `Node` 是 `#[pin_data]` Rust 结构（[`drivers/android/binder/node.rs:191`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/drivers/android/binder/node.rs#L191)），字段是 `Arc<Process>`、`LockedBy<...>` 这些 Rust 类型，`ListArc::try_from_arc(self.clone())` 自己造链表项（[`node.rs:373`](https://github.com/KMiri-rs/linux/blob/1a86c8d19dbc194298bec82102f3f3b19464eada/drivers/android/binder/node.rs#L373)）。它跟 C binder 共享的只是 `ptr/cookie` 这些 u64 编号，不是结构体内存。

---

**一句话总结**：refcount 的**语义**借了 C（`refcount_t` 饱和计数），`rb_node`/`list_head` 这些**链接字段**借了 C；但 `Arc`/`ListArc` 的**分配和生命周期是 Rust 完全自管的**，C 侧只持有 Rust 通过 `ForeignOwnable` 递出去的裸指针。"C 创建、Rust 包装"这个模式真实存在，但它对应的是 `interop/list.rs` 和 `rbtree.rs` 那套，不是 `list.rs` 的 `ListArc`。

这也正好回到上一个问题——正因为 `list.rs` 的 `ListArc` 是 Rust 自己管内存的纯 Rust 链表，它才更值得（也更容易）放进 Miri 验证；而 `interop/list.rs` 依赖真实 C 分配，Miri 反而不好测。要不要我在 `list.rs` 下加一个 `#[cfg(miri)]` 的测试模块试试？
