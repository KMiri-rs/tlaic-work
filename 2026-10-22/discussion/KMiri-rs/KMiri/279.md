# 【笔记】切片引用 as_ptr 越过范围访问 = Stacked Borrows subobject provenance UB

## Body

## TL;DR

一个「切片引用 → `as_ptr` → 越过切片范围访问大分配」的写法被 KMiri 报 UB。定位到这是 **Stacked Borrows 的 subobject provenance（子对象 provenance）规则**在起作用，并非 KMiri 的 bug，而是 SB 模型有意为之的限制；同一写法在 Tree Borrows 下不报错。上游正讨论是否对数组/切片放宽这条限制。

[playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2024&gist=89fbbda335b18c3fc76db4d155fddc23)

## 起因：一个手工构造的 DST 测例

下面这个测例里，`Dst { data: [()] }` 的唯一字段是 ZST 切片，因此整个 `Dst` 是零大小的 DST。`ok()` 与 `ub()` 的唯一区别是：前者直接对裸指针做 `cast`，后者先 `&*local` 重借用成 `&Dst` 再做 `cast`：

```rust
#![allow(unused)]

#[repr(C)]
struct Dst {
    data: [()],
}

impl Dst {
    unsafe fn from_raw<'a>(ptr: *const usize, nbits: usize) -> *const Dst {
        let data: *const [()] = core::ptr::slice_from_raw_parts(ptr.cast(), nbits);
        data as _
    }

    fn as_ptr(&self) -> *const usize {
        (self as *const Dst).cast::<usize>()
    }

    fn as_ptr2(this: *const Self) -> *const usize {
        this.cast::<usize>()
    }
}

#[test]
fn ok() {
    let backing: [usize; 1] = [0xfeed_face_cafe_beef];
    let local = unsafe { Dst::from_raw(backing.as_ptr(), 1) };
    let word = unsafe { *Dst::as_ptr2(local) };
    assert_eq!(word, backing[0]);
}

#[test]
fn ub() {
    let backing: [usize; 1] = [0xfeed_face_cafe_beef];
    let local = unsafe { Dst::from_raw(backing.as_ptr(), 1) };
    let word = unsafe { *Dst::as_ptr(&*local) };
    assert_eq!(word, backing[0]);
}
```

## 定位：与现有测例逐字同源

这条诊断与 [tests/fail/stacked_borrows/zst_slice.rs](https://github.com/KMiri-rs/miri/blob/af87bdb338e347872bc2429308e2865901488bfb/tests/fail/stacked_borrows/zst_slice.rs) 完全一致，那句 "zero-size retag" 就来自 [src/borrow_tracker/stacked_borrows/diagnostics.rs:90](https://github.com/KMiri-rs/miri/blob/af87bdb338e347872bc2429308e2865901488bfb/src/borrow_tracker/stacked_borrows/diagnostics.rs#L90)：

```rust
struct Dst { data: [()] }          // 手工 DST（零大小 retag）      → UB
let s = &a[0..0]; *s.as_ptr().add(1)  // 零长子切片（零大小 retag） → UB（zst_slice.rs）
```

两者都是「零大小 retag」产生的 tag 在 borrow stack 里根本不存在——`ub()` 里 `&*local` 对零大小 DST 的重借用，与 `zst_slice.rs` 里 `&a[0..0]` 的零长切片重借用，是同一件事。

## 最简复现（非零长版本）

```rust
fn main() {
    let a = [1, 2, 3];
    let s = &a[0..1];
    unsafe {
        *s.as_ptr().add(1);   // 越过 s 的范围 [0x0..0x4]，落到 a[1]
    }
}
```

- `&a[0..1]` 的 retag 范围只有 `[0x0..0x4]`（子切片），不是整个 `a`。
- `s.as_ptr()`（`self as *const [T] as *const T`）继承这个 span。
- `.add(1)` 落到 `[0x4]`，那里 borrow stack 里没有对应 tag → SB 报 "tag does not exist"。

## 根因：subobject provenance

这是 Stacked Borrows 的 **subobject provenance** 规则：由某个引用/指针只能访问它指向的那个子对象（这里是数组元素/子切片），不能靠指针算术去访问兄弟子对象。动机不是「那块内存不能读」，而是保住 `foo(&p.f1); p.f2 = 4;` 这类重排/写穿优化。

## SB vs TB：同一写法结论相反

- **SB**：按「字节范围」维护 tag 栈，retag 会把新 tag 的范围压到子切片，越界访问时「栈里没有这个 tag」→ UB。
- **TB**：按「tag 树 + 状态机」维护权限，reborrow/投影 **不缩小范围**，只改状态；没有外来访问把 tag Disable 时，子 tag 在整个分配内读写都合法 → 不报错。

上游 Ralf 的原话（[#622](https://github.com/rust-lang/unsafe-code-guidelines/issues/622)）：*"In SB, both are UB because all retags implicitly limit the accessible range of a reference. In TB, we don't do that and hence have no subobject provenance."*

不过 Ralf 也承认，严格的 SB 风格 subobject provenance 对编译器有好处——他在 #622 里提到了 LLVM 那边可能的改动（[llvm/llvm-project#218413](https://github.com/llvm/llvm-project/pull/218413)）：

> FWIW, the discussion in llvm/llvm-project#218413 shows some potential benefits of a strict, SB-style subobject provenance for the compiler: it becomes a lot simpler to define the aliasing restrictions, at least for sized types.

但他紧接着的结论是权衡不划算：

> But given the enormous footgun potential, I am not sure that that's worth it.

## 上游相关 issue

- [#134 — raw pointer usable only for `T` too strict?](https://github.com/rust-lang/unsafe-code-guidelines/issues/134)：原始版本，`&val[0] as *const u8; *ptr.add(1)`，收集了大量中招案例（rand、hashbrown、`Rc::into_raw`、FFI 柔性数组等）。
- [#622 — No subobject provenance for arrays/slices](https://github.com/rust-lang/unsafe-code-guidelines/issues/622)：直接命中本案例，示例代码几乎一模一样；Ralf 倾向「Even C allows this」而放宽，现处于 `proposed-final-comment-period`，但挂着 `consistency` / `data` / `types-as-arrays` 三个 concern，尚未落地。
- [#419 — Should we have subobject provenance?](https://github.com/rust-lang/unsafe-code-guidelines/issues/419)：父问题。
- [#256 — &Header, reading data past the end](https://github.com/rust-lang/unsafe-code-guidelines/issues/256)、[#276 — Stacked Borrows cannot handle `extern type`](https://github.com/rust-lang/unsafe-code-guidelines/issues/276)：同机制的结构体/`extern type` 变体。
