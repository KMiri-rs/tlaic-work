# miri 如何处理 volatile 这类 Rust intrinsic ？

## Body

我已经把整条处理链路追清楚了。结论先行:**kmiri(以及上游 Miri)根本没有为 `volatile` 写任何专门代码**——volatile 类 intrinsic 全部退化成"普通内存读写",由 rustc 核心解释器处理。

## 涉及哪些 intrinsic

Rust 里"volatile"这一族 intrinsic 都在 `core::intrinsics` 里声明(无 MIR 函数体,`must_be_overridden = true`):

- `volatile_load` / `volatile_store` —— 稳定封装是 `core::ptr::read_volatile` / `write_volatile`
- `volatile_set_memory`
- `unaligned_volatile_load` / `unaligned_volatile_store`(较新,不要求对齐)
- 已废弃的 `volatile_copy_memory` / `volatile_copy_nonoverlapping_memory`

## 处理路径

调用入口在 `src/intrinsics/mod.rs:43` 的 `call_intrinsic`。注意它第一行就先让核心引擎试一次:

```rust
// src/intrinsics/mod.rs:54
if this.eval_intrinsic(instance, args, dest, ret)? {
    return interp_ok(None);
}
```

`volatile_load`/`volatile_store`/`volatile_set_memory` **没进 kmiri 自己的 `emulate_intrinsic_by_name` 那个大 match**(那个 match 只处理 `atomic_*`、`simd_*`、`ptr_mask`、`abort` 等),而是被 `eval_intrinsic`(rustc_const_eval 核心解释器)直接吃掉了。核心引擎里的实现就是普通读写:

```rust
// rustc_const_eval/src/interpret/intrinsics.rs(你的 toolchain rustc-src 里)
sym::volatile_load => {
    let [ptr] = args else { span_bug!(...) };
    let place = self.deref_pointer(ptr)?;   // 解引用
    self.copy_op(&place, dest)?;            // 从 *ptr 读,写到返回位置
}
sym::volatile_store => {
    let [ptr, val] = args else { ... };
    let place = self.deref_pointer(ptr)?;
    self.copy_op(val, &place)?;             // 把 val 写进 *ptr
}
sym::volatile_set_memory => {
    self.write_bytes_intrinsic(ptr, val_byte, count, "volatile_set_memory")?;
}
```

也就是说 `volatile_load` = `copy_op(&*ptr, dest)`、`volatile_store` = `copy_op(val, &*ptr)`,和普通 load/store 完全等价,没有任何 volatile 语义的特判。

## 在 kmiri 的 GenMC 模式下

这些普通读写会经过 `Machine` 的 hook:

- `before_memory_read`(`src/machine.rs:1766`)/ `before_memory_write`(`src/machine.rs:1807`)
- GenMC 分支里调用 `genmc_ctx.memory_load`(`machine.rs:1785`)/ `memory_store`(`machine.rs:1825`)
- 最终落到 `handle_non_atomic_load` / `handle_non_atomic_store`(`src/concurrency/genmc/mod.rs:720` / `:781`)

关键点:**volatile 访问在 GenMC 眼里被当作"非原子(non-atomic)"访问**转发,而不是原子访问。这符合 Rust 语义——`volatile` 只阻止编译器对**单次访问**做删减/重排,它**不提供原子性、不建立 happens-before**,多个线程对同一 volatile 位置并发读写仍然构成数据竞争(UB)。所以 GenMC 会照常做数据竞争检测,而不是像 `atomic_*` 那样走 `handle_atomic_load/store`(mod.rs:706/745)。

## 为什么不需要专门实现 volatile

`volatile` 存在的唯一意义是**对抗编译优化**(消除冗余 load/store、死存储消除、指令重排)。而 Miri/kmiri 是解释器:

- 它按 MIR 顺序**逐条执行、一次不多一次不少**,本来就绝不会省略或重排任何一次内存访问;
- 因此 volatile 与普通读写的行为完全一致,直接把 intrinsic 映射成 `copy_op` 就够了。

验证用的测试就是 `tests/pass/intrinsics/volatile.rs`,里面 `volatile_store` 后 `volatile_load` 读回并断言,以及 `tests/pass/write-bytes.rs` 里 `volatile_set_memory` 与 `write_bytes` 行为一致的断言——都能印证"volatile 即普通内存操作"这一点。
