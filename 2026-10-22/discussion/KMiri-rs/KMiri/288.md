## Body

本文以 `tests/fail/kmiri/ordinary-thread-return-no-join.rs` 为例，走读 kmiri（基于 Miri 的向量时钟数据竞争检测器）一步步检测出 data race 的完整过程。所有代码位置均用指向 commit `51b4943a419e76b2eb4b20454e564623753fce3d` 的永久链接标注。

## 被测代码与预期

[`tests/fail/kmiri/ordinary-thread-return-no-join.rs:8`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/tests/fail/kmiri/ordinary-thread-return-no-join.rs#L8)：

```rust
fn main() {
    let _thread = std::thread::spawn(|| {
        unsafe { VALUE = 1 };                      // (1) 子线程非原子写
        FINISHED.store(true, Ordering::Relaxed);   // relaxed 原子写
    });
    while !FINISHED.load(Ordering::Relaxed) {      // relaxed 原子读自旋
        std::thread::yield_now();
    }
    std::hint::black_box(unsafe { VALUE });        // (2) main 非原子读 —— 触发检测
}
```

这是一个回归测试：验证 kernel task 的返回交接（handoff）**不会**把普通 `std::thread` 的返回误当成一次隐式 join。`VALUE` 是 `static mut`，`FINISHED` 是 relaxed 原子标志。relaxed 只保证执行顺序、不提供同步，因此 `VALUE` 上的写-读之间没有 happens-before，必须报 race（对应 [`tests/fail/kmiri/ordinary-thread-return-no-join.stderr:1`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/tests/fail/kmiri/ordinary-thread-return-no-join.stderr#L1) 里的 "Data race detected between (1) non-atomic write ... and (2) non-atomic read"）。

## 0. 数据结构和检测入口

检测算法是**向量时钟（vector clock）**。核心状态：

**每个字节一份元数据** [`src/concurrency/data_race.rs:268`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L268)：

```rust
struct MemoryCellClocks {
    write: (VectorIdx, VTimestamp),  // 最后一次非原子写：谁写的、什么时刻
    write_type: NaWriteType,          // Allocate / Write / Deallocate
    read: VClock,                     // 自上次写以来，所有非原子读的时钟（join 起来）
    atomic_ops: Option<Box<AtomicMemoryCellClocks>>, // 原子访问的额外时钟
}
```

**每个线程一个向量时钟** [`src/concurrency/vector_clock.rs:261`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/vector_clock.rs#L261)，概念上是 `Vec<(线程索引, 时间戳)>`。happens-before 的判定就是比较两个 `VClock` 是否满足 `<=`（`impl PartialOrd for VClock`）。

**所有非原子读写都从这里进** [`src/machine.rs`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/machine.rs)：

- [`before_memory_read:1766`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/machine.rs#L1766) → `data_race.read_non_atomic(...)`
- [`before_memory_write:1807`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/machine.rs#L1807) → `data_race.write_non_atomic(...)`

`VALUE = 1` 和 `black_box(VALUE)` 就分别走这两条路径。

## 1. 静态变量 `VALUE` 的初始状态

`VALUE` 是 `static mut`，属于 `MemoryKind::Global`。分配时 [`VClockAlloc::new_allocation:1030`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L1030) 把它的 cell 初始化为"时间戳 0 的分配写"：

```
VALUE 的 cell:  write = (main_index, 0),  write_type = Allocate,  read = {},  atomic_ops = None
```

`write_type = Allocate` 时 `write.1 = 0`，代表"这段内存还没有被真正写过"。

## 2. 主线程 spawn 子线程 → 建立 happens-before

`std::thread::spawn` 最终走到 [`thread_created:1729`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L1729)：

```rust
self.multi_threaded.set(true);                 // 开启多线程检测
created.join_with(current);                    // 子线程继承父线程时钟
current.increment_clock(current_index, ..);    // 父线程推进
created.increment_clock(created_index, ..);    // 子线程推进
```

假设 main 此时时钟为 `[main:1]`，spawn 之后：

```
main  = [main:2]
child = [main:1, child:1]      // 子线程拿到新索引 1
```

这是关键的合法同步：**main 在 spawn 之前的所有动作 happens-before 子线程的所有动作**。但方向是单向的——子线程的动作**不会**自动回传给 main。

## 3. 子线程 `unsafe { VALUE = 1 }`（非原子写）

`before_memory_write` → [`write_non_atomic:1269`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L1269) → [`non_atomic_write_detect:667`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L667)：

```rust
// Check synchronization with non-atomic accesses.
if !(self.write_was_before(&thread_clocks.clock) && self.read <= thread_clocks.clock) {
    return Err(DataRace);
}
// Record this access.
self.write = (index, thread_clocks.clock[index]);   // ← 记录"谁、何时写的"
self.write_type = write_type;
self.read.set_zero_vector();
```

[`write_was_before:446`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L446)：

```rust
fn write_was_before(&self, other: &VClock) -> bool {
    self.write.1 <= other[self.write.0]   // 上一次写的时间戳 ≤ 当前线程时钟里那个索引的值
}
```

此时上次写是 `Allocate`（时间戳 0），`0 ≤ 任何值` 成立，检查通过，**不报 race**。随后记录：

```
VALUE 的 cell:  write = (1, 1)          ← 子线程(child=索引1)在时刻1写的
```

## 4. 子线程 `FINISHED.store(true, Relaxed)`

原子操作走 [`validate_atomic_op:1574`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L1574)，`Relaxed` 对应 [`store_relaxed:554`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L554)：

```rust
fn store_relaxed(...) -> Result<(), DataRace> {
    self.atomic_write_detect(thread_clocks, index, access_size)?;
    let atomic = self.atomic_mut_unwrap();
    atomic.sync_vector.clone_from(&thread_clocks.fence_release);  // 只写 fence 时钟
    Ok(())
}
```

对照 [`store_release:540`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L540) 是 `atomic.sync_vector.clone_from(&thread_clocks.clock)`——**把当前线程完整时钟放进 `sync_vector` 供别人 acquire**。而 `store_relaxed` 不这么做，所以它**不产生 release**，后续 relaxed load 也拿不到任何同步信息。这正是测试注释里说的 "a relaxed flag orders execution but does not synchronize"。

`FINISHED` 的 cell 记录了子线程的原子写，但**不改变 main 与 child 之间没有 happens-before 这一事实**。

## 5. 主线程自旋 `while !FINISHED.load(Relaxed)`

[`load_relaxed:524`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L524)：

```rust
fn load_relaxed(...) -> Result<(), DataRace> {
    self.atomic_read_detect(...)?;
    if let Some(sync_clock) = sync_clock.or_else(|| self.atomic().map(|a| &a.sync_vector)) {
        thread_clocks.fence_acquire.join(sync_clock);   // 只 join 进 fence_acquire
    }
    Ok(())
}
```

关键：`load_relaxed` 只把 `sync_vector` join 进 **`fence_acquire`（fence 专用时钟）**，而 [`load_acquire:507`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L507) 才是 join 进 **`clock`（真正 happens-before 时钟）**。所以 relaxed load **不会**把子线程的时钟 acquire 进 main。

结果：自旋结束后，**main 的时钟里 child 那一维仍然是 0**：

```
main  = [main:2]      （child 维 = 0，因为从没和 child 同步过）
```

## 6. 主线程 `black_box(unsafe { VALUE })`（非原子读）→ 报错

`before_memory_read` → [`read_non_atomic:1219`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L1219) → [`non_atomic_read_detect:640`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L640)：

```rust
// Check synchronization with non-atomic writes.
if !self.write_was_before(&thread_clocks.clock) {
    return Err(DataRace);
}
```

- cell 里上次写是 `write = (1, 1)`（子线程时刻 1）。
- 当前读线程是 main，`write_was_before` 比较：`self.write.1 (1) <= main_clock[1] (0)` → **false**。

于是返回 `Err(DataRace)`，`read_non_atomic` 随即调用 [`report_data_race:1115`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L1115)：

```rust
} else if mem_clocks.write.1 > active_clocks.clock[mem_clocks.write.0] {
    write_clock = mem_clocks.write();
    (AccessType::NaWrite(mem_clocks.write_type), mem_clocks.write.0, &write_clock)
}
```

这里 `1 > 0` 成立，所以定位到"对立的那个访问"就是子线程的非原子写，`other_thread = 索引1`。最终 `TerminationInfo::DataRace` 带着两边信息抛出，正好对应 `.stderr` 里的两处 `-->` 指向：

```
op1 = non-atomic write  on thread `unnamed-ID`  (VALUE = 1)
op2 = non-atomic read   on thread `main`        (black_box(VALUE))
```

## 7. 为什么"被 join"就能消除这个 race（反过来印证边界）

如果主线程显式 `_thread.join()`，走 [`after_join:1221`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/thread.rs#L1221) → [`thread_joined:1799`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L1799) → [`acquire_clock:1934`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/data_race.rs#L1934)：

```rust
pub fn acquire_clock(&self, clock: &VClock, threads: &ThreadManager) {
    let (_, mut clocks) = self.thread_state_mut(thread);
    clocks.clock.join(clock);   // 把被 join 线程的终止时钟 join 进当前线程
}
```

join 之后 main 的时钟变成 `[main:2, child:≥1]`，第 6 步的 `1 <= main_clock[1]` 变为 **true**，`write_was_before` 通过，不再报 race。

而 commit 51b4943 新增的隐式 join [`src/concurrency/thread.rs:1069`](https://github.com/KMiri-rs/miri/blob/51b4943a419e76b2eb4b20454e564623753fce3d/src/concurrency/thread.rs#L1069) **只有当线程在 `thread_map` 里（即 kernel task）才执行**，普通 `std::thread` 不在其中，因此不会走 `thread_joined`，race 得以保留——这正是 `tests/fail/` 期望的结果。

---

**一句话总结这条因果链**：`spawn` 建立了 main→child 的 happens-before（第 2 步），但反向不成立；child 写 `VALUE` 记录下"索引 1 时刻 1"（第 3 步）；relaxed 的 flag 读写都不做 release/acquire（第 4、5 步），所以 main 的时钟里 child 维一直是 0；当 main 非原子读 `VALUE` 时，发现"上一次写的时间戳 1 > 自己时钟里对方维的值 0"，`write_was_before` 返回 false → 报 race（第 6 步）。
