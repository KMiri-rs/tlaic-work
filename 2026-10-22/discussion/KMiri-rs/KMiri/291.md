# KMiri 如何支持 Rust for Linux - kmiri 内核模块与 kmiri 解释器通过 RPC 直通

## Body

> 我希望修改 miri （代码在 ../kmiri ），增加对 rust for linux 测例运行的支持；
>  这会遇到很多 bindings ，kmiri 肯定解释不过去；
>  目前我的第一个思路是替换一些 bindings 代码为 Rust ，然后 `make -f makefile.local miri-unit` 可以跑 kernel bitmap 模块的几个测试；
>  但这种方式不具备拓展性，比较不可能替换所有  bindings；
>  所以我的另一个思路是写一个 kmiri 内核模块，然后与 kmiri 进程交互，当 kmiri 解释遇到内核 binding，那么向  kmiri 内核模块通信，透传参数，这样
>  binding 过程虽然是一个黑盒无法被 kmiri 解释和检测（也会带来漏报），但至少处理了无法执行下去的问题。你觉得这个设计思路的可行性如何

你的第二个思路（`kmiri` ↔ “内核模块黑盒代理”）**概念上可行，但我不建议作为主线方案**。  
我的判断是：**能做出“跑得动”，很难做成“可信、可扩展、可维护”**。

**为什么不推荐黑盒代理**
- `Miri/KMiri` 的价值是检查 UB 与内存语义；一旦把 binding 变成黑盒 RPC，最关键的语义正好被绕开，漏报会系统性变多。
- kernel binding 大量涉及指针、生命周期、别名、并发与原子语义；跨进程/跨模块序列化后，这些语义很难保真。
- 还会引入 ABI 漂移、版本耦合、时序非确定性（竞态/死锁）、调试复杂度飙升。
- 最后你会得到一个“能继续执行”的系统，但结果解释性和可信度会持续下降。

**你现在第一种思路的问题**
- 手工替换 bindings 为 Rust mock 能快速起步，但确实不具扩展性（你判断对）。

**更可行的主线（建议）**
- 不做“真实内核模块代理”，改做 **KMiri 内部 shim/模型层**：
  - 按 binding 分层：`纯常量/布局`、`纯函数`、`状态函数`、`硬件/不可建模`。
  - 前三类做可组合 shim（优先最小语义模型），最后一类显式 `unsupported` 或 `skip`。
- 建立 **allowlist + 覆盖率报表**：每次测试输出“哪些 binding 被真实建模、哪些被黑盒/跳过”。
- 默认 **fail-closed**（未知 binding 报错），按测试集逐步放开，避免 silently pass。
- 自动生成 shim 骨架（从 bindgen 输出/符号表），减少手工维护成本。

**结论**
- 你的“黑盒代理”可作为临时逃生通道，但不应是长期架构。  
- 长期应是：**KMiri 内部语义 shim + 分层建模 + 覆盖可观测性**，这样才有拓展性和可信度。

如果你愿意，我可以下一步帮你把这个方案细化成一个 3 阶段落地路线图（先跑通 bitmap，再扩到 alloc/sync 子集）。
