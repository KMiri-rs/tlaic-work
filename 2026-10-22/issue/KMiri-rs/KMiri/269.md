# Miri Stacked Borrows report on Rust-for-Linux bitmap ZST-DST pointer access pattern (may be modeling mismatch)

## Body

## Summary

Running Rust-for-Linux bitmap unit tests under Miri reports a Stacked Borrows UB diagnostic on ZST-DST pointer conversion/access patterns.

Concretely, this is triggered by the `Bitmap` representation (`data: [()]`) plus conversion from `&Bitmap` to `*const usize`, followed by raw pointer reads.

## Concrete diagnostic (specific case)

In `bitmap_borrow` (and similarly in other bitmap tests), Miri reports:

- `attempting a read access ... but that tag does not exist in the borrow stack`
- with help text indicating a zero-size retag from the `&Bitmap` -> raw pointer conversion.

Relevant code in Linux tree (permanent links):

- `as_ptr` conversion on `Bitmap`: https://github.com/KMiri-rs/linux/blob/f92bb7cf463773d9c44ad4838c30ed371c8d383b/rust/kernel/bitmap.rs
- bitmap tests module (`bitmap_borrow`, etc.): https://github.com/KMiri-rs/linux/blob/f92bb7cf463773d9c44ad4838c30ed371c8d383b/rust/kernel/bitmap.rs

## Minimal reproductions (generalization ladder)

Below are the 3 reduced tests directly (from specific to minimal), all preserving the same core pattern:

1. construct DST with ZST backing field (`data: [()]`) from raw pointer metadata,
2. convert `&Dst` to `*const usize`,
3. perform raw dereference/read.

<details>
<summary><code>access_beyond_dst_ptr_reproduce</code> (closest to bitmap flow)</summary>

```rust
#[repr(C)]
struct Bitmap {
    data: [()],
}

impl Bitmap {
    unsafe fn from_raw<'a>(ptr: *const usize, nbits: usize) -> &'a Bitmap {
        let data: *const [()] = core::ptr::slice_from_raw_parts(ptr.cast(), nbits);
        unsafe { &*(data as *const Bitmap) }
    }

    fn as_ptr(&self) -> *const usize {
        (self as *const Bitmap).cast::<usize>()
    }

    fn len(&self) -> usize {
        self.data.len()
    }

    fn next_bit(&self, start: usize) -> Option<usize> {
        if start >= self.len() {
            return None;
        }

        for index in start..self.len() {
            let word = index / usize::BITS as usize;
            let bit = index % usize::BITS as usize;
            let value = unsafe { *self.as_ptr().add(word) };
            if (value & (1usize << bit)) != 0 {
                return Some(index);
            }
        }

        None
    }
}

#[test]
fn access_beyond_dst_ptr_reproduce() {
    let backing: [usize; 2] = [0, 0];
    let nbits = 2 * usize::BITS as usize;

    let bitmap = unsafe { Bitmap::from_raw(backing.as_ptr(), nbits) };
    assert_eq!(None, bitmap.next_bit(0));
}
```

## Why this may be a false-positive-for-kernel-semantics (or at least non-actionable UB claim)

Important context: this diagnostic likely does **not** directly indicate real kernel UB in the original C-backed path.

In Rust-for-Linux production behavior, memory access semantics are in/through the binding side (kernel C implementation). For Miri testability, we currently replace parts of that behavior with Rust-side emulation. The Stacked Borrows complaint appears tied to Rust-side representation/provenance modeling of the emulated path, not necessarily to an actual bug in the kernel-side memory access semantics.

So the issue is likely at least partly a modeling mismatch:

- Miri strict provenance / Stacked Borrows expectations for this ZST-DST conversion pattern,
- versus how bitmap memory is actually represented and accessed across Rust/C boundary in kernel reality.

## Questions

1. Is this pattern expected to be rejected by Miri's Stacked Borrows model (even if operationally acceptable for current Rust-for-Linux/C interop design)?
2. Should KMiri treat this as:
   - a known modeling limitation,
   - a case to suppress/relax for kernel-oriented runs,
   - or a real bug that should be refactored away in Rust bitmap representation?
3. If refactoring is preferred, what representation/provenance-safe pattern do you recommend for this bitmap wrapper style?
