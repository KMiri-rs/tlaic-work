# Rust for Linux: the missing semantics of `krealloc_node_align`

## Body

https://github.com/KMiri-rs/miri/pull/64#discussion_r4390733566 points out three arguments align、flags、nid  are not handled at all. 

We should handle  align and flags in `krealloc_node_align`.

<details><summary>nid seems negligible</summary>
<p>

`nid` 是 **NUMA node id**,指定这块内存希望从哪个 NUMA 节点分配。它在 `krealloc_node_align` 的语义里是**性能/局部性偏好**,不参与 Rust 侧的任何正确性语义。

## 具体含义

| 项   | 说明                                                                                                                                                                                                                                     |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 类型 | `int`(参数名 `nid` = NUMA node id)                                                                                                                                                                                                       |
| 取值 | `0..MAX_NUMNODES-1` 表示具体节点;`NUMA_NO_NODE`(即 `-1`,见 [include/linux/nodemask_types.h:15](https://github.com/KMiri-rs/linux/blob/3c2b1d286661a66e2375ad8bb2df52e047ef77ce/include/linux/nodemask_types.h#L15))表示"无所谓,就近分配" |

## 它的作用:只是一个"倾向",不是硬约束

1. **`NUMA_NO_NODE` 时**:就地分配,默认取当前 CPU 所在节点(`numa_mem_id()`)。例如页分配路径 [include/linux/gfp.h:230-234](https://github.com/KMiri-rs/linux/blob/3c2b1d286661a66e2375ad8bb2df52e047ef77ce/include/linux/gfp.h#L230-L234) 里:

   ```c
   if (nid == NUMA_NO_NODE)
       nid = numa_mem_id();
   ```

2. **对 `krealloc` 尤其弱**:只有当重分配**需要搬迁**时,nid 才会被用来挑新块的节点;如果能**原地扩展**(新大小落在原 slab 桶内,返回原指针),nid 根本不被使用。即使搬迁,SLUB 也只是"优先"从该节点分配 —— 除非 flags 里带 `__GFP_THISNODE` 才变成硬约束(见 [include/linux/gfp.h:266-269](https://github.com/KMiri-rs/linux/blob/3c2b1d286661a66e2375ad8bb2df52e047ef77ce/include/linux/gfp.h#L266-L269) 的注释:*"preferring the node given as nid ... Otherwise node must be valid and online"*)。

## Rust 侧如何传入

Rust 侧把它包装成 `NumaNode`([rust/kernel/alloc.rs:127-149](https://github.com/KMiri-rs/linux/blob/3c2b1d286661a66e2375ad8bb2df52e047ef77ce/rust/kernel/alloc.rs#L127-L149)):

- `NumaNode::new(node)` 会校验 `0 <= node < MAX_NUMNODES`,非法返回 `EINVAL`;
- `NumaNode::NO_NODE` 就是 `NUMA_NO_NODE`(-1),表示无偏好。

再经 `ReallocFunc::call` 以 `nid.0` 原样透传给 C 的 `krealloc_node_align`([rust/kernel/alloc/allocator.rs:125](https://github.com/KMiri-rs/linux/blob/3c2b1d286661a66e2375ad8bb2df52e047ef77ce/rust/kernel/alloc/allocator.rs#L125))。

## 对 kmiri 的结论

正因为它只影响**物理内存落在哪个 NUMA 节点**,不改变:
- 分配/释放是否成功(成功与否只由大小、flags、内存压力决定),
- 返回指针的 Rust 语义(对齐、大小、内容保留、旧指针失效),

所以在"kmiri 只关心 Rust 语义"的前提下,**`_nid` 被 shim 丢弃是完全正确、且应当如此的**。这也是我上一轮把 `nid` 和 `ZERO_SIZE_PTR` 一起归为"可接受的简化"、而把 `align`/`flags` 单独挑出来的原因 —— 后两者会实质改变 Rust 语义,`nid` 不会。

</p>
</details>
