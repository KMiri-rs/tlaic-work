## Body

Close https://github.com/KMiri-rs/KMiri/issues/36

The kmiri-side fix was to make the provenance model match the way OSTD initializes typed allocations.

### Problem

After `kern_miri_retype_pages` marks a physical page as `Typed`, OSTD later reaches it through integer-derived raw pointers. In Miri, that is only valid if the allocation has an exposed tag that can grant the access in the borrow stack.

Before the fix, kmiri only updated the page-state model:

- `Unused` -> `Untyped` -> `Typed`

but it did **not** make the corresponding allocation/tag visible to the borrow tracker in a way that raw/wildcard pointers could actually use.

So Miri could resolve the address, but when the write happened it had no suitable exposed tag with write permission.

### Fix strategy

I fixed that in `kmiri/src/alloc_addresses/mod.rs` by making typed-slot allocation registration do two things:

1. Register the allocation address in `alloc_addresses`
2. Explicitly expose the allocation’s root tag in the borrow tracker

Concretely:

- after `set_address(...)`, I call `root_ptr_tag(...)`
- then I call `expose_tag(...)` for that tag

I applied the same logic to the CPU-local allocation path as well, because it uses the same int-to-ptr-style access pattern later.

### Why this works

Miri’s wildcard/raw-pointer access path looks up an allocation by address, but it will only grant the access if the allocation has an exposed tag with the right permission in the borrow stack.

By exposing the root tag at allocation registration time, the typed allocation becomes writable through the later integer-derived pointer access that OSTD uses during initialization.

### In short

The fix was not “change the page type.”
It was “make the typed allocation’s provenance visible to Miri so raw-pointer writes can legally reach it.”
