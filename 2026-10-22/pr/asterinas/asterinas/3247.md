## Body

## Summary

Implements the design proposed in #3188 — concise subsystem-scoped visibility for `aster-kernel` — and rolls it out beyond the pilot. Three commits:

1. **Add short-vis-path crate** — new `ostd/libs/short-vis-path` proc-macro crate.
2. **Replace `pub(in crate::*subsystem)` by `pub(in subsystem)` in kernel** — applies the macro across `kernel` (54 files).
3. **Replace `pub(in crate::*::subsystem)` by `pub(in subsystem)` in ostd** — applies the macro across `ostd` (48 files).

Closes #3188.

## Background

#3188 (RFC, `C-design-proposal`) argues that the kernel's `pub(in crate::a::b::subsystem)` paths impose three concrete costs:

1. **Verbosity** — 35+ characters before the item keyword, vs. 11 for `pub(crate)`.
2. **Refactor friction** — promoting or renaming a subsystem forces sweeping multi-file edits.
3. **Reading friction** — a long path obscures the very locality information it is supposed to convey.

The RFC's grep on `main` counted 89 occurrences in `kernel/` alone across 7 subsystem paths. The same pain exists in `ostd/`, which is why this PR widens the rollout.

The proposed mechanism is a file-level inner attribute:

```rust
#![short_vis_path::add(procfs)]

pub(in procfs) struct ProcDir { ... }  // → pub(in crate::fs::fs_impls::procfs)
```

The macro infers the full path from the source file's location and rewrites only `pub(in <name>)` whose `<name>` was declared in `add(...)`. Other visibilities (`pub`, `pub(crate)`, `pub(super)`, `pub(in crate::...)`, private) are untouched.

## Implementation

`ostd/libs/short-vis-path` exposes a single attribute proc-macro `add` used as an inner attribute. It accepts the three call shapes specified in the RFC:

```rust
#![short_vis_path::add(procfs)]                                  // infer from file location
#![short_vis_path::add(procfs, fs)]                              // multiple short names
#![short_vis_path::add(procfs = crate::fs::fs_impls::procfs)]    // explicit override
```

Resolution algorithm (`ostd/libs/short-vis-path/src/args.rs`, `ExpandedPath::new`):

1. `proc_macro::Span::call_site().local_file()` + `CARGO_MANIFEST_DIR` ⇒ relative source path.
2. Strip the leading `src/`; strip `/mod.rs` or `.rs` from the tail.
3. Split on `/` to get the module path starting at `crate`.
4. For each bare-ident argument, `rposition` the named segment (deepest match wins). On miss, panic with a message naming both the unknown ident and the file's inferred path.

Rewriting (`AddArguments::visit_visibility_mut`):

- A `VisitMut` traversal touches **every** `Visibility::Restricted` whose path is a single ident in the table — items, methods, associated items, **and struct fields**. (This goes beyond Known Limitation 3 in the RFC, which stated field-level rewriting was not implemented in the POC.)
- `pub(in path) macro foo` is not yet parseable by `syn`, so `Item::Verbatim` is patched at the token-tree level (`replace_verbatim_vis_path`).

## Differences from the RFC

- **Field-level support.** Implemented; the RFC's Known Limitation 3 no longer applies.
- **Extra usage guidelines.** `short_vis_path` should only be used for deep subsystem paths that need repeated restricted visibility, when `pub(super)`/`pub(self)` are not enough, and the path must still expand to an ancestor module.

What is unchanged from the RFC: the user-visible syntax, the resolution heuristic (deepest match, override form as escape hatch), the visibility set the macro is allowed to touch, the two nightly features (`custom_inner_attributes`, `proc_macro_hygiene`), and the "opt-in, additive, no central registry" property.

## Known limitations (unchanged from the RFC where applicable)

- **Nightly feature flags.** `custom_inner_attributes` + `proc_macro_hygiene` are now load-bearing for `ostd` and `kernel`. Both have long-standing tracking issues; stabilisation should be monitored.
- **Obscure error diagnostics.** In some edge cases (listed below), the unstable `custom_inner_attributes` is incomplete and has bugs.
  - https://github.com/os-checker/short-vis-path/issues/1
  - https://github.com/os-checker/short-vis-path/issues/2
  - https://github.com/os-checker/short-vis-path/issues/3
- **`<crate>/src/...` layout assumed.** Files outside that layout, `#[path = "..."]` overrides, or name collisions can use the `name = crate::path` override form.
